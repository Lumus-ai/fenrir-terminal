# Fenrir Terminal — Changelog

## RAM guard v2 — 07.11.2026 (пороги и эскалация, авточистка)

- Пороги те же, что в v1: OK ≥500 / WARN 300–499 / CRIT <300 МБ
  MemAvailable. `ram_guard()` не менялся по поведению (те же пороги,
  тот же возврат (МБ, статус)); добавлены `_classify_ram()` и
  `_read_mem_available_mb()` как переиспользуемые помощники.
- `ram_guard_check()` (`fenrir_term.py`, stdlib only): эскалация по
  уровням. OK — ничего не делает. WARN — запись в `logs/ram-guard.log`
  + лёгкая чистка безопасного мусора. CRIT — повторная проверка через
  5 с: не подтвердился — чистка отменяется (защита от ложных
  срабатываний); подтвердился — запись в `logs/ram-guard.log` и в
  `logs/ram-warnings.log` (формат v1) + полная чистка с ротацией
  логов. Защита от параллельного запуска — lock `logs/ram-guard.lock`
  (битый старше 10 мин пересоздаётся).
- Авточистка удаляет ТОЛЬКО allowlist-мусор
  (`_collect_cleanup_candidates`): `__pycache__` под терминалом и
  оркестрой, старые `*.log.1` в `logs/` (старше 7 дней), старые
  `/tmp/lix-queue-*.jsonl` (старше 7 дней). Перед удалением — проверка
  занятости через `/proc/*/cwd` и `/proc/*/fd` (активный serve/batch
  защищает путь). Никогда не трогаются: runs/, state/,
  PLAN-EXTENDED.md, код, свежие очереди и файлы пользователя.
  Процессы не убиваются вообще. Ротация: лог > 1 МБ -> `.1`; свежий
  `.1` не затирается.
- `bin/ram-watchdog.sh` v2: тонкая обёртка над `fenrir_term.py guard`;
  `--dry-run` — только лог, ничего не удаляет; fallback на проверку
  v1 (free < 300 МБ -> строка в ram-warnings.log), если python-часть
  не сработала. Выход всегда 0. Команда: `fenrir watchdog`
  (и `fenrir_term.py guard [--dry-run]` напрямую).
- Из спеки пачек Lix 1035/1041/1042 взята только суть (пороги,
  эскалация, dry-run, проверка занятости, ротация). НЕ брались:
  psutil, пути /opt/fenrir и /var/log, «Shadow Alert», убийство
  процессов, канарейки/FreeRTOS из «правок» — в реальном терминале
  этого нет.
- Проверки живьём 07.11.2026: `test_ram_guard_v2.py` — 36 проверок
  (границы 500/300, dry-run и реальная чистка на фейковом дереве,
  защита занятого пути, ротация, lock, неизменность `ram_guard()`) —
  все прошли. Живой dry-run при RAM 398–451 МБ [WARN]: удалило бы
  2 объекта (`__pycache__` терминала и оркестры, ~136 КБ), реально
  ничего не удалено, lock не остался, `ram-warnings.log` не создан
  (он только для CRIT). `fenrir status` до и после — v1.3.1, формат
  RAM-строки тот же; версия терминала не менялась.
- `fenrir doctor` — без изменений в логике; на момент проверки
  показывал FAIL только по probe (health-файл устарел на 407 мин —
  предсуществующее состояние, к guard не относится).

## v1.3 — 06.11.2026 (сильный агент)

- Новые инструменты агента (`fenrir_agent.py`): `edit_file` (замена
  точного фрагмента; отказ, если фрагмент найден 0 или >1 раз, файл
  не трогается), `search` (regex по рабочей папке, file:line, max 50),
  `run_tests` (py_compile всех .py + pytest -q, если есть тесты).
  Проверены локально без модели: edit ok / not-found / search / py_compile OK.
- Маршрутизация моделей: `--kind code` (по умолчанию) —
  klinch7/gpt-6-luna → klinch6/gpt-6-luna → lix/qwen3.8-max →
  lix/deepseek-v4.1-flash; `--kind text` — lix/qwen3.8-max →
  deepseek-v4.1-flash → kimi-k3 → klinch7/gpt-6-luna. `--connector`/
  `--model` ставят свою пару первой. Фолбэк при 403/429/5xx и обрыве
  соединения — на следующий живой в цепочке. Мёртвые модели Lix
  (claude-opus-5.5, claude-sonnet-5.5, gpt-6-astra) и klinch/klinch2
  (лимит исчерпан) в цепочках отсутствуют.
- Очередь задач: `fenrir_agent.py --file tasks.jsonl` — каждая строка
  {"task", "workdir", "kind?", "max_steps?"}; свой лог шагов на задачу
  и `summary.json` с итогом ok/fail по каждой.
- Верификация по умолчанию: после записи агент проверяет файлы на
  диске сам (`verify_workdir`): HTML — начало с <!DOCTYPE html>,
  единственность </body> и </html>, отсутствие текста после </html>,
  дубли id; Python — py_compile. При проблемах — дописывает сам
  (edit_file/append_file), не отдаёт недоделку.
- System-промпт агента с правилами сборки: чанки append_file
  1000-1500 символов, </body></html> только в последнем куске,
  сверка с хвостом через read_file, без дублей секций.
- `fenrir agent` — команда терминала: обёртка над fenrir_agent.py
  (`fenrir agent --task ... --workdir ...` / `--file tasks.jsonl`).
- max-steps по умолчанию поднят с 5 до 30 (сайт 30+ КБ требует
  ~20 append-чанков).
- Приёмочный тест ПРОЙДЕН живьём 06.11.2026: Луна через `fenrir agent`
  с нуля собрала сайт-визитку в `~/workspace/sait-mebel-vizitka-v13/`
  за один запуск (20 шагов, exit 0, модель klinch7/gpt-6-luna).
  Первый прогон дал 20 346 символов — ниже порога 30 КБ, поэтому
  второй прогон расширил сайт до 33 536 символов (725 строк): добавлены
  FAQ (6 вопросов), отзывы (3), галерея (6 работ), этапы расширены.
  Независимая проверка файла на диске: начинается с <!DOCTYPE html>,
  заканчивается </html>, </body> и </html> по 1 разу, 9 секций
  открыто/закрыто поровну, дублирующихся id нет, плейсхолдеров нет.
  Ручных правок в файл не вносилось. Оговорка: второй прогон вернул
  exit 1 («max steps reached») — файл к тому моменту уже был полным,
  Луна сожгла шаги 23–25 на лишние поисковые проверки вместо ответа;
  агент пока не распознаёт «работа готова», если модель продолжает

## v1.2 — 06.11.2026 (надёжность)

- Watchdog-cron каждые 5 минут (`fenrir-orchestra-watchdog`): запускает
  `fenrir-orchestra/watchdog.sh`, молчит, пока serve отвечает; при
  недоступности — перезапускает и докладывает. Живая проверка:
  serve убит в 05:02 по Самаре, результат срабатывания крона (~05:06)
  — см. ниже после подтверждения.
- User-Agent везде в движке: единый `USER_AGENT = "fenrir-agent/1.0"`
  в `fenrir_orchestra.py` (chat и /v1/models). Дополнительно найден и
  исправлен настоящий источник ложного «lix dead HTTP 403» в probe:
  единственный вызов probe ротировался на перепроверку мёртвой модели
  (claude-opus-5.5 / claude-sonnet-5.5), и её 403 маркировал мёртвым
  весь провайдер, хотя живые модели отвечали. Теперь при упавшей
  перепроверке probe делает второй вызов живой моделью и пишет его
  в `probe_live`; статус провайдера — по живой модели. Проверено:
  probe показывает `lix alive — 1 + 1 = 2 (мёртвая claude-sonnet-5.5
  всё ещё HTTP 403)`. Живой `run` на lix/qwen-flash тоже проверен.
- `fenrir doctor` — самопроверка одной командой: serve, свежесть probe
  (< 1 часа), RAM, диск (файловая система рабочей папки /home/hatch,
  а не маленький overlay корня /), дедлайн Lix. Вывод OK/FAIL по
  пунктам, exit 1 при любом FAIL. Проверено живьём при убитом serve:
  FAIL serve, остальные OK.
- `fenrir limits` — лимиты всех ключей Klinch одной таблицей
  (использовано / осталось / сброс по Самаре / всего) + остаток дней
  Lix. Проверено живьём: klinch и klinch2 — 0 осталось, klinch6 —
  24,0 млн, klinch7 — 40,0 млн (использовано 24 тыс).
- `fenrir usage` — токены за день (по Самаре) из runs/*/meta.json,
  по провайдерам, пишет `state/usage-<дата>.json`. Проверено живьём:
  06.11 — 13 вызовов, lix 7 тыс токенов. Ограничение: считаются только
  вызовы движка (meta.json); прямые вызовы агента fenrir_agent.py
  в runs/ не пишутся и в учёт не попадают.
- `health_summary()` теперь учитывает `probe_live`: если перепроверка
  мёртвой модели упала, а живая ответила — провайдер ok с пометкой
  про мёртвую модель.
- `fenrir down` починен: `pkill -f` теперь с шаблоном `serv[e]` —
  раньше паттерн совпадал с собственной командной строкой и убивал
  вызвавший шелл.
