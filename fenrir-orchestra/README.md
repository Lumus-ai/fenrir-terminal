# Fenrir-Orchestra

Личная лёгкая оркестра Фенрира. Python stdlib only — без Bun, без TS-сервера,
без фонового агента group-чата, без pip install.

## Чем отличается от оригинала (orchestra-app)

| Проблема оригинала (проверено 06.11.2026) | Как лечится здесь |
|---|---|
| Совет Оркестры мёртв: агент group-чата ни разу не запускается, токены 0, сообщения в очереди | Никакого агента чата вообще. Консилиум = 6 параллельных прямых API-вызовов + синтез; всё сразу на диск |
| Длинные финалы теряются: ответ ровно 6144 токена → пустой финал | `max_tokens` по умолчанию 2000; каждый ответ пишется на диск СРАЗУ, атомарно (tmp + `os.replace`); пустой ответ = failure, не success |
| Klinch: дневной лимит 40 млн, сброс 01:00 по Самаре; все не-Grok имена = grok-4.7 | Фолбэк-цепочки по ролям; мёртвая модель уходит в `state/cooldown.json` на 30 мин и пропускается |
| Anymodel через оркестру не делает tool calls | Anymodel используется только для коротких текстовых ответов (роль `text`) |
| Lix топ-модели (opus-5.5, sonnet-5.5, gpt-6-astra) с 06.11 ~03:54 дают 403 | В цепочках только живые модели: deepseek-v4.1-flash/pro, glm-5.3-prime, kimi-k3, qwen3.8-max, qwen-flash; мёртвые перепроверяются ротацией в каждом probe (один короткий вызов на провайдера) — могут ожить |

## Тариф Lix: 260 RPM, 2M TPM, 6 параллельных (чек Shadow 06.11 ~04:14)

Безлимит на весь оплаченный период до **09.11.2026**, суммарный объём
не ограничен. Параметры: **260 запросов/мин, 2 000 000 токенов/мин,
до 6 одновременных параллельных соединений**. Зафиксировано также
в `providers.json` (`tariff_lix`).

## Как выжимать лимит

- **6 параллельных, не 1 за раз.** Одиночный последовательный вызов
  использует <1% лимита (2M TPM): один ответ ~2–5 тыс. токенов за
  секунды — потолок не достигается никогда. Поэтому `council` по
  умолчанию 6 воркеров, а `batch` гоняет очередь пулом ровно 6.
  Больше 6 одновременных вызовов нигде не делается — это лимит тарифа.
- **Очередь без пауз.** `batch --file tasks.jsonl`: как только воркер
  освободился, он сразу берёт следующую задачу, без искусственных
  задержек. Если задач меньше 6 — просто меньше воркеров.
- **Большие чанки.** `max_tokens` по умолчанию 2000 — кап 6144 не
  трогать (на нём финалы теряются, проверено 06.11.2026). Длинные
  задачи резать на чанки по 2000 и гнать их batch-очередью.
- **Не тратить Lix на пустое.** Короткие пробы — только в `probe`
  (один вызов на провайдера). Мёртвые топ-модели перепроверяются
  ротацией, а не сплошным перебором.
- **Считать факт, не надеяться.** Каждый `batch` пишет
  `summary.json`: суммарные токены, затраченное время, фактические
  TPM и RPM — сверять с лимитом 2M TPM / 260 RPM.

## Lix: приоритет №1 до 09.11.2026

Ключ Lix — 3 дня безлимита, **дедлайн понедельник 09.11.2026** (Shadow
06.11 ~04:11: «надо все соки из него выжимать»). Правила:

- **Lix — строгий приоритет №1 во всех ролях.** Klinch/Anymodel — только
  фолбэк, когда все живые Lix-модели мертвы (cooldown или ошибка).
  Цепочки в `providers.json` перечисляют все живые Lix-модели раньше
  любого не-Lix провайдера.
- Тяжёлые задачи — в первую очередь на Lix, пока ключ жив.
- Живые Lix на 06.11 ~04:00: `deepseek-v4.1-flash`, `deepseek-v4-pro`,
  `glm-5.3-prime`, `kimi-k3`, `qwen3.8-max`, `qwen-flash`.
- Мёртвые (403) на 06.11 ~03:54: `claude-opus-5.5`, `claude-sonnet-5.5`,
  `gpt-6-astra` — **перепроверять, не хоронить**: каждый `probe` тратит
  свой единственный короткий вызов Lix на одну мёртвую модель по ротации
  (не чаще раза в 30 мин на модель, состояние — `state/lix_dead_recheck.json`).
  Ожила — cooldown снимается, модель снова в цепочках.
- `probe` печатает остаток времени до дедлайна и пишет его в
  `runs/health-<дата>.json` (`lix_deadline`, `lix_time_left`).
| Ключи в env/файлах | Ключей нет нигде: каждый запрос подписывается суррогатом через `dynamic_credentials.add_surrogate_to_request`, редиректы запрещены (`NoRedirect`) |

## Запуск

```sh
cd ~/workspace/fenrir-orchestra
python3 fenrir_orchestra.py status                    # состояние, exit 0 всегда
python3 fenrir_orchestra.py probe                     # здоровье провайдеров; exit 2 если все мертвы
python3 fenrir_orchestra.py run --task "..." --role code
python3 fenrir_orchestra.py council --task "..."      # 6 воркеров + синтез
python3 fenrir_orchestra.py batch --file tasks.jsonl  # очередь, пул 6 воркеров
python3 fenrir_orchestra.py serve --port 4097         # только 127.0.0.1
```

## Команды

- **probe** — `GET /v1/models` у каждого провайдера + один короткий chat
  `1+1=` (`max_tokens` 20) на одной живой модели каждого провайдера.
  Баг 06.11.2026: probe строил `base_url + "/v1/models"`, а base_url уже
  `.../v1` — получался `/v1/v1/models` → 404 и ложный `models_ok=false`
  при живом chat. Исправлено: `models_url()` берёт host-корень
  (`.../v1` + `/models`). Для Lix единственный вызов ротируется
  на перепроверку мёртвых (403) моделей — одна за probe, не чаще раза
  в 30 мин на модель. Отчёт: `runs/health-<дата>.json` + таблица alive/dead
  с причиной (403/429/timeout) + остаток времени до дедлайна Lix 09.11.2026.
  Мёртвая модель → `state/cooldown.json` на 30 мин.
- **run** — `--role code|review|text`, `--max-tokens` (по умолчанию 2000),
  timeout 300 с, ретрай 1 раз на следующий фолбэк при 403/429/502/пустом
  ответе. Пишет `runs/<id>/answer.md` + `meta.json` (provider, model,
  реальный model из ответа, finish_reason, usage, время) сразу при успехе.
- **council** — 6 параллельных воркеров (ThreadPoolExecutor, кап тарифа):
  coder, reviewer, skeptic, architect, tester, simplifier — каждый в свой
  `runs/<id>/worker-N.md`; затем короткий вызов сводит их
  в `runs/<id>/synthesis.md`. Если синтез упал — в `synthesis.md`
  ручная сводка-заглушка со списком файлов воркеров, а не пустота.
- **batch** — очередь из `tasks.jsonl`, каждая строка
  `{"task": "...", "role": "code|review|text"}`. Пул ровно 6 воркеров
  (меньше, если задач меньше), без пауз между задачами. Каждый результат —
  сразу на диск `runs/<batch>/task-N/answer.md` + `meta.json` с usage.
  В конце — `runs/<batch>/summary.json`: задач всего/успешно/упало,
  суммарные токены, затраченное время, фактические TPM и RPM.
- **serve** — крошечный HTTP на `http.server`, только `127.0.0.1:4097`:
  `GET /health` → `{ok, providers, uptime}`, `POST /run {task, role}` →
  запускает run и возвращает id + файлы, `GET /runs` → список.
  Авторизации извне localhost не надо — порт не слушает внешний интерфейс.
- **status** — читает `state/` и последние runs, печатает провайдеры,
  cooldown и последние задачи. Exit 0 даже если все провайдеры мертвы.

## Роли и модели (см. `providers.json`)

| Роль | Цепочка фолбэка (Lix всегда первый, Klinch/Anymodel — только после всех живых Lix) |
|---|---|
| code | lix/deepseek-v4.1-flash → lix/kimi-k3 → lix/qwen3.8-max → lix/deepseek-v4-pro → klinch/gpt-6-astra (=grok-4.7) |
| review | lix/glm-5.3-prime → lix/deepseek-v4-pro → lix/kimi-k3 → klinch/gpt-6-astra |
| text | lix/qwen-flash → lix/kimi-k3 → lix/deepseek-v4.1-flash → anymodel/gpt-6.1-sol → anymodel2/gpt-6.1-sol → klinch/gpt-6-astra |

## Watchdog / автоперезапуск

`systemd --user` в этой песочнице недоступен (нет bus) — проверено.
Вместо него cron каждые 5 минут:

```cron
*/5 * * * * /home/hatch/workspace/fenrir-orchestra/watchdog.sh
```

`watchdog.sh` проверяет `curl http://127.0.0.1:4097/health`; если нет
ответа — запускает `serve` в фоне через `nohup`, лог — `logs/watchdog.log`.

## Файлы

- `fenrir_orchestra.py` — единый CLI (stdlib only)
- `providers.json` — маршруты: baseURL, коннектор, модели по ролям (без ключей!)
- `watchdog.sh` — проверка + перезапуск serve
- `state/cooldown.json` — мёртвые модели на 30 мин
- `runs/` — ответы, мета, отчёты здоровья (`health-<дата>.json`)
- `logs/` — логи serve/watchdog
- `WORK_LOG.md` — журнал работ

## Exit codes

- `status` — всегда 0 (честный отчёт, даже если всё мертво).
- `probe` — 0 если жив хотя бы один провайдер, 2 если мертвы все.
- `run` / `council` — 0 при успехе, 1 если все модели цепочки упали
  (council — 0 если жив хотя бы один воркер).
